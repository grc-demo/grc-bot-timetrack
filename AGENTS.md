# AGENTS.md — правила работы над grc-bot-timetrack

## Назначение и рамки

Разрабатываем Telegram-бота учёта времени по заказам и пяти этапам, описанным в [README.md](README.md). Первая версия фиксирует интервалы и даёт руководителю сводки в часах, но **не** рассчитывает себестоимость. Не выдавайте проектные предположения за согласованные бизнес-правила: спорные решения из раздела «Вопросы перед реализацией» README сначала согласуйте.

## Предлагаемый стек

- Python 3.12+; зависимости через `uv` и зафиксированный lockfile.
- `aiogram` 3, асинхронный Telegram Bot API; один экземпляр long polling на токен.
- PostgreSQL; асинхронный SQLAlchemy и Alembic для схемы/миграций. Не создавать схему автоматически при каждом запуске приложения.
- `pytest` (+ `pytest-asyncio`) для тестов, Ruff для форматирования и линтинга.
- Dockerfile для бота, PostgreSQL — отдельный сервис/ресурс. Coolify передаёт переменные окружения и подключение к БД; база должна сохранять данные при пересоздании контейнера бота.

Конкретные версии фиксируйте в `pyproject.toml` и lockfile при реализации; не подменяйте реальные зависимости и миграции псевдокодом.

## План структуры (папки ещё не созданы)

```text
src/timetrack_bot/
  __main__.py       # точка входа polling
  config.py         # конфигурация из окружения
  bot/              # handlers, клавиатуры, проверки доступа
  domain/           # сущности и правила интервалов/отчётов
  db/               # модели SQLAlchemy, репозитории, сессии
  services/         # сценарии старта, завершения и сводок
migrations/         # Alembic: версионируемые изменения БД
tests/              # unit и интеграционные тесты
Dockerfile          # контейнер приложения
compose.yaml        # локальная PostgreSQL (при добавлении)
pyproject.toml      # метаданные и зависимости
uv.lock             # зафиксированные версии
.env.example        # только имена переменных и безопасные примеры
```

Handlers не должны содержать SQL или расчёт бизнес-правил; зависимости Telegram и БД держите на границах. Храните начало и окончание как UTC timestamps с учётом часового пояса; не округляйте длительность в базе до целых часов. Атомарно обеспечьте не более одной активной записи на сотрудника (в том числе при повторных нажатиях и конкурирующих запросах). Проверяйте роли и доступ к заказу на сервере, а не только видимость кнопок. Запросы отчётов фильтруйте по разрешённым данным.

## Разработка и проверки

**Пока команды ниже — целевой интерфейс после появления кода и файлов конфигурации; сейчас их выполнять нечего.** При реализации поддерживайте их актуальными в README и проверяйте в CI:

```bash
uv sync --dev
# Запустить локальную PostgreSQL, если добавлен compose.yaml:
docker compose up -d db
# Задать BOT_TOKEN и DATABASE_URL через локальное окружение (не коммитить значения).
uv run alembic upgrade head
uv run python -m timetrack_bot

uv run ruff check .
uv run ruff format --check .
uv run pytest
```

Интеграционные тесты запускайте на **отдельной тестовой БД**; тесты миграций и транзакций не должны обращаться к рабочей БД. Минимальные будущие проверки: старт/финиш, повторные нажатия, конкурирующий старт, отсутствие активной записи, необязательный комментарий, сумма по заказу/этапу/периоду, ограничения доступа и границы дат. При изменении поведения обновляйте README и тесты вместе с кодом.

## Деплой и безопасность

Docker-образ запускает один polling-процесс; не масштабируйте его на несколько реплик с одним токеном. В Coolify подключите управляемую/отдельную PostgreSQL с постоянным хранилищем; `DATABASE_URL` и `BOT_TOKEN` задавайте секретами окружения. Миграции запускайте как отдельный контролируемый шаг до обновления приложения, а не параллельно из нескольких реплик. Не печатайте токен, DSN с паролем или текст личных комментариев в логах. Перед деплоем нужны резервное копирование БД и проверенный способ восстановления.

## Что нельзя трогать без отдельного согласования

- Не коммитить `.env`, токены, пароли, дампы БД, личные данные сотрудников и реальные комментарии.
- Не удалять или переписывать применённые миграции и рабочие данные; изменения схемы — новыми миграциями с понятным порядком выката.
- Не менять произвольно справочник этапов, правила подсчёта длительности, роли и доступ к заказам: это влияет на будущую себестоимость.
- Не выполнять destructive SQL, не запускать тесты или миграции на production-базе.
- Не коммитить прямо в `main`, не делать force-push и не сливать PR самостоятельно; работайте в отдельной `task/*` ветке и отдавайте PR на проверку.
